incitez：受信任的引用
標準，經過驗證 — 且更快。

eyecite 是提取法律引用的事實標準（它為 CourtListener 和 Caselaw Access Project 提供支援）。incitez 與之匹配 — 經過驗證 — 在完整簡報上熱啟動速度約為 31 倍（典型的一次性運行約為 64 倍），並且在文件結構可靠的情況下，當事人歸屬更準確。 限制是重點：首先是同等，然後是速度，然後是我們可以誠實地做得更好的地方。

驗證的同等性
324 = 324

在真實上訴簡報上與 eyecite 進行逐條引用匹配，並由 CI 中的 215/215 差異門控 提供支援。不是「看起來很接近」 — 而是機械驗證。在 1.7 MB 語料庫中，引用一致性保持在 2,160 對 2,159 — 速度並非以更差的召回率換取。

速度
快約 64 倍

典型的一次性運行約 90 頁的上訴簡報：incitez 約 30 毫秒，而 eyecite 每次都重新支付約 170 毫秒的 Python/模型啟動時間。熱啟動且僅引擎運行時約為 31 倍（31.6 毫秒對 987 毫秒）；差距隨著簡報大小和引用密度而增加。

當事人歸屬
183 對 0

在瀏覽器演示中的真實上訴簡報上：350 引用，183 清晰歸屬的當事人，而樸素提取有 324 引用和 0 當事人。

誠實的框架

incitez 不聲稱在所有地方都超越標準 — 它聲稱 可驗證地與之匹配，然後只在確實可以做得更好的地方做得更好。

  • 原始 PDF 文字： eyecite 找到的相同引用 — 在完整簡報上熱啟動速度約為 31 倍，一次性運行約為 64 倍。
  • 在結構可靠的情況下（例如，帶有清晰當事人行的 權威列表）：incitez 正確歸屬當事人 — 「Albritton」為原告 — 而樸素提取將標題混入名稱中（「權威列表 … Albritton」）。
  • 在結構不可靠的情況下： incitez 保持同等水平而不是猜測。只有在確實可行時才提供超越。

如何驗證

每次構建都會針對相同的語料庫運行 incitez 和 eyecite，並在任何差異時使 CI 失敗 — 這是一個 差異預言機，而不是手動挑選的演示。這是 MFIC — Mecha 在其工作中應用相同的紀律：作者無法悄悄地通過錯誤輸出的檢查。對於法律受眾來說，這就是「相信我」和「這是門控」之間的區別。

幕後原理

純 Zig 核心（無 I/O）→ C FFI 邊界 → 原生 CLI 和 WebAssembly 模組 — 相同的引擎在終端機中直接運行，也在瀏覽器演示中運行。引文語法和報告數據來自 Free Law Project (reporters-db, courts-db, eyecite)，根據其 BSD 2-Clause 條款使用。

原始碼可用性： incitez 根據商業原始碼許可證 (BUSL-1.1) 提供原始碼 — 閱讀、建置和運行原始碼；它會延遲轉換為開源。在 GitHub 上查看原始碼 →
