MFIC — Mechanisch-Falsifizierbare Unabhängige Kontrolle ist eine Disziplin genau dafür: unabhängige Prüfungen bei jeder Übergabe, die ihr Urteil aus dem Vertrag oder den Daten ableiten, niemals aus der Aussage des Produzenten, und die Befugnis haben, abzulehnen oder zu stoppen. Es ist das interne Kontrollmodell hinter Sarbanes-Oxley (COSO) — Aufgabentrennung, präventive und detektive Kontrollen, Audit-Trails, angemessene Sicherheit — mit dem LLM (oder einem eiligen Menschen) als neuer, nicht vertrauenswürdiger Partei.

Für regulierte, hochriskante Arbeiten ist das der Unterschied zwischen „die KI hat es gesagt“ und einer Antwort, die Sie bei einer Prüfung verteidigen können. Es ist die Disziplin hinter allem, was Mecha baut — und der Grund, warum ein Verifizierungsergebnis hier mit einem Gate, nicht mit einem Versprechen kommt.

Wie man Code oder Daten vertraut, die ein fehlbarer Autor — ein LLM oder ein eiliger Mensch — stillschweigend korrumpieren könnte. Die rote Phase von TDD liefert nur F (ein Test kann auslösen); MFIC fügt die anderen drei hinzu. Es ist das COSO / Sarbanes-Oxley interne Kontrollmodell, mit dem LLM als neuer, nicht vertrauenswürdiger Partei.

Definition: eine unabhängige Prüfung an einer Übergabegrenze, die ihr Urteil aus dem Vertrag oder den Daten ableitet — niemals aus der Darstellung des Produzenten — und die Befugnis hat, abzulehnen, zu stoppen oder zu steuern.

Lackmustest: wenn derselbe Agent sowohl die Prüfung als auch das geprüfte Ding geschrieben hätte, könnte es bei falscher Arbeit bestehen? Ja → manipulierbar, nicht MFIC. Nein → MFIC.

Jedes Wort ist tragend:

  • Mechanisch — Fälle maschinell durchsucht, nicht handverlesen. ¬M → Auslassungsfehler.
  • Falsifizierbar — jeder Fall eine beißende Widerlegung, die man nicht vorher arrangieren kann. ¬F → leere grüne Tests oder schwache Orakel („stürzt nicht ab“ verbirgt falsche Ausgabe).
  • Unabhängig — Wahrheitsquelle kausal unabhängig vom Produzenten (≡ Aufgabentrennung: Ersteller ≠ Prüfer). ¬I → kollusive Tests, die einen blinden Fleck teilen; die Achse, die TDD offen lässt.
  • Kontrolle — eine Basislinie plus die Befugnis, Fehler zu verursachen oder zu steuern. ¬C → Telemetrie, die beobachtet, aber niemals blockiert.

Zwei Regime:

  • Statisch (Code verifizieren, in CI) — Erschöpfung, Differential, Metamorph, Eingabemutation, eigenschaftsbasiert, Perf/Leak-Gates. Detektiv.
  • Dynamisch (Zustand im Flug verifizieren, in Produktion) — Stage-Boundary-Verträge, Schema-/Invarianz-Erhaltung, Reject-to-Previous-Schleifen. Präventiv + korrektiv.

Greifen Sie zuerst nach dem stärksten, billigsten: endlicher Bereich → erschöpfen Sie ihn; Inverse → Round-Trip decode(encode(x))==x; Referenz → Differential; Transformationsinvariant → Metamorph; kann bekanntermaßen gute Eingaben korrumpieren → Eingabemutation (eine Abdeckungszahl, keine Bool); sonst → eigenschaftsbasiert + schrumpfen. Bevorzugen Sie das Orakel, das der Autor nicht geschrieben hat — orakelfrei schlägt einen vom Autor erstellten „erwarteten Wert“, der selbst falsch sein könnte.

Eingabemutation, speziell: drehen Sie jedes Bit/Byte einer bekannten gültigen Eingabe um und stellen Sie sicher, dass der Verifizierer sie jetzt ablehnt; der erkannte Anteil misst, wie viel des Formats er tatsächlich einschränkt — und verwandelt „Ich validiere das gesamte Format“ in eine Zahl, die niemand halluzinieren kann. Halten Sie es ehrlich: Paaren Sie es mit einem Spezifitätskorpus (alle gültigen Eingaben müssen passieren, sonst erzielt ein Alles-Ablehnungs-Prüfer 100%), und bewerten Sie nur Muss-Erkennen-Regionen (Padding / CRC-ausgeschlossene Bytes sind legitime Don't-Cares).

Leitplanken: gewöhnliche Validierung scheitert normalerweise an I (ein Agent definiert das Schema und produziert dagegen) oder C (es protokolliert nur). Ein Nur-Warn-Monitor ist M-F-I, aber ¬C — Telemetrie, kein Gate; eine Prüfung, die den Build fehlschlagen lässt, ist vollständig MFIC. Beweise sind konstitutiv — eine Kontrolle ohne Spur wurde nicht ausgeführt; versionieren Sie ihre Messhistorie nach Commit + Hardware. Statistische Mitglieder geben angemessene Sicherheit, keinen Beweis — den anerkannten Standard, keine Mängel.

Stand der Technik: Mutation, Metamorph, Differential, eigenschaftsbasiertes Testen, Fehlerinjektion (Software V&V); Aufgabentrennung, präventive/detektive/korrektive Kontrollen, Audit-Trail, Kontrolle der Kontrollen, angemessene Sicherheit (COSO / Sarbanes-Oxley).

Dies ist die Arbeitszusammenfassung. Die vollständige technische Abhandlung — die Unabhängigkeitsachse in der Tiefe, das Produzenten-/Genehmiger-Muster, die Eskalation von der Richtlinie zu blockierenden Gates zu kryptografischen Kontrollen und fünf ausgearbeitete Beispiele — befindet sich in der vollständigen MFIC Methodik.
